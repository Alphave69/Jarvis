# Джарвис — личный календарь с ИИ-ассистентом

Соло-проект. Владелец знает Python и Node.js/JS. Общение и UI — на русском.

## Стек

- **Next.js (App Router) + TypeScript + Tailwind CSS**
- **Supabase** — Postgres + Auth (email + пароль; пользователь один, создаётся вручную в панели Supabase, регистрация закрыта), доступ к данным только через RLS
- **PWA** — `manifest.webmanifest` + свой `sw.js` (без плагинов), ставится на экран iPhone и работает на ПК.
  Стратегия кеша: **network-first для HTML и данных, cache-first только для неизменяемой статики** (`/_next/static/*`, иконки). После деплоя приложение не должно показывать старую версию.
- Вся логика, работающая с данными и (в будущем) с ИИ, живёт на сервере: Server Actions / route handlers. Клиент — только интерфейс.

### Особенности Next.js 16 (важно!)

- Версия новее, чем знания модели: перед кодом сверяться с документацией в `node_modules/next/dist/docs/` (см. `AGENTS.md`).
- **`cacheComponents` выключен** (решение после шага 2). Приложение целиком персональное: сессия в cookies, данные под RLS → «use cache» неприменим, статическая оболочка почти пустая. Зато с ним каждый `Date.now()`/`new Date()` при пререндере — ошибка, а календарь весь из дат. Без него страницы под входом просто динамические (`ƒ`), `redirect()` из `requireUser()` — настоящий HTTP-редирект. Скелетоны загрузки — через `loading.tsx`.
  - Если в будущей мажорной версии Next флаг станет обязательным: чтение данных держать в async-компонентах страниц/`loading.tsx`, чтобы миграция свелась к `<Suspense>` + `await io()` перед датами.
- `middleware.ts` переименован в `proxy.ts`, функция — `proxy`.
- Шрифты — системные (`-apple-system`), без `next/font/google`.

## Структура папок (целевая)

```
src/
  app/
    layout.tsx               # корневой layout, тёмная тема, PWA-мета
    login/page.tsx           # вход: почта + пароль
    (app)/                   # всё, что требует входа
      page.tsx               # месяц: ?m=YYYY-MM; карточка дня поверх: &d=YYYY-MM-DD
      event/[id]/page.tsx    # карточка события + заметки (форму уточнить на шаге 6)
  components/                # MonthView, DaySheet (карточка дня), NewEventForm, TimeZoneSync…
  lib/
    supabase/                # env.ts, server.ts (клиент для сервера), proxy.ts (updateSession)
    data/                    # серверный слой доступа к данным: auth.ts (requireUser), events.ts, notes.ts
    actions/                 # Server Actions — тонкая обёртка над lib/data (auth.ts, events.ts, notes.ts)
    dates.ts                 # хелперы дат без внешних библиотек ('YYYY-MM-DD', UTC-арифметика)
    event-input.ts           # проверка входных данных события (чистые функции)
    timezone.ts              # пояс пользователя из cookie `tz` (ставит TimeZoneSync)
    colors.ts                # 7 цветов событий (системные цвета iOS)
    database.types.ts        # типы схемы БД (вручную, по миграциям; только `type`, не `interface`)
  proxy.ts                   # (бывший middleware.ts в Next 16) обновление сессии, редирект на /login
supabase/
  migrations/                # SQL-миграции, применяются вручную в Supabase SQL Editor
tests/
  unit/                      # чистые функции (даты, проверка ввода) — npm test
  e2e/                       # браузер против production-сборки — npm run test:e2e
  mock-supabase/             # имитация Supabase (Auth + PostgREST) и тестовые данные
  run.mjs                    # кроссплатформенный запуск (PowerShell / Linux)
playwright.config.ts
public/
  manifest.webmanifest, sw.js, icons/
```

`lib/data/*` — единственное место, где пишутся запросы к БД. На этапе 3 эти же функции станут инструментами Джарвиса.

## Дорожная карта

1. **Каркас** — календарь (месяц/день), события, заметки к событиям, вход, PWA. Без ИИ. ← *текущий этап*
   - 1.x (после этапа 1, до этапа 2 — по решению владельца): **повторяющиеся события** (каждый день / неделю / месяц / год, исключения). См. «Расширение схемы» ниже.
2. **Джарвис-чат** — бэкенд на Claude API, персонаж в духе Джарвиса («сэр», сухой британский юмор). Комментирует события и заметки (`events.jarvis_comment`), задаёт наводящие вопросы.
3. **Tool use** — Джарвис сам создаёт, переносит, удаляет события.
4. **Telegram-бот** — напоминания (поля `reminder_*` уже есть в БД), утренняя сводка, быстрый ввод.
5. **Долгая память** — привычки, люди, проекты.
6. **Агент на ПК** — файлы, ссылки, запуск программ.

### Навигация и UI-решения
- **Карточка дня = вид «день».** Отдельной страницы `day/[date]` нет: тап по дню открывает `DaySheet` поверх месяца, URL `/?m=…&d=YYYY-MM-DD` (ссылка и «Назад» работают). Телефон — шторка снизу (свайп вниз закрывает), ПК — окно по центру. Нативный `<dialog>` (`showModal`): Esc, фокус, инертный фон.
- Создание в два тапа: тап по дню → фокус в поле названия → Enter/«Добавить». Умолчание — «весь день», синий. Остальное под «Ещё». Пустой день — «Пока пусто».
- Месяц и карточка открываются мгновенно (`useOptimistic`), данные догружаются; после мутации — `refresh()` из Server Action.
- iOS открывает клавиатуру только на `focus()` внутри жеста — скрытое поле `keyboardProxy` в `MonthView` принимает фокус в момент тапа.
- «Сегодня» — по поясу браузера (cookie `tz`), не сервера.

## Модель данных — ключевые решения

- Событие = `event_date` (date) + `start_time`/`end_time` (time) + `timezone` (IANA). Не `timestamptz`, чтобы «весь день» не уезжал при смене пояса.
- **Через полночь:** если `end_time < start_time`, конец — на следующий день (`event_date + 1`). В вид «день» такое событие попадает в день начала; в следующий день — как «продолжение» (только отображение).
- Ограничения в БД: «весь день» ⇔ оба времени `null`; иначе `start_time` обязателен; `end_time <> start_time` (равные — неоднозначно: 0 или 24 ч); при `reminder_enabled` нужно `reminder_minutes_before`. `notes(event_id, user_id)` → составной FK на `events(id, user_id)`: заметка всегда принадлежит владельцу события.
- Data API отдаёт `date` как `'YYYY-MM-DD'`, `time` как `'HH:MM:SS'` — не пропускать дату через `new Date()` (сдвиг пояса). Выборка месяца начинается на день раньше — ради событий через полночь.
- Цвет = категория, 7 фиксированных значений.
- `reminder_*` — только хранятся до этапа 4. `jarvis_comment` — для этапа 2.

### Напоминания: от какого момента считаются минуты (решение для этапа 4)

Схема не меняется: `reminder_minutes_before integer >= 0` для обоих видов событий, отличается только точка отсчёта (в поясе события `events.timezone`):

| Событие | Точка отсчёта | Момент напоминания | Варианты в форме |
|---|---|---|---|
| со временем | `event_date` + `start_time` | начало − N минут | за 5 / 15 / 30 мин, за 1 час, за 1 день |
| весь день | `event_date` 09:00 | 09:00 − N минут | **«В день события в 9:00»** = `0`, **«Накануне в 20:00»** = `780` |

- Для «весь день» форма показывает только эти два варианта вместо минут; умолчание — «в день события в 9:00».
- При переключении «весь день» ⇄ «со временем» выбор напоминания сбрасывается на умолчание нового вида (минуты одного вида бессмысленны для другого).
- До этапа 4 форма для «весь день» ещё предлагает минуты; такие значения по этой договорённости означают «за N минут до 9:00» (например, «за 1 день» = накануне в 9:00) — данные не ломаются.
- Отправка (Telegram) и переход формы на эти варианты — этап 4.

### Расширение схемы: повторяющиеся события (не в этапе 1)

- В `events` добавляется `rrule text` (строка RFC 5545, напр. `FREQ=WEEKLY;BYDAY=MO,WE`) и `rrule_until date`. Событие с `rrule` — «шаблон серии», экземпляры вычисляются на сервере при выборке месяца, в БД не размножаются.
- Отдельная таблица `event_exceptions (event_id, occurrence_date, is_cancelled, override_* …)` — для «удалить/изменить только это вхождение».
- Заметки и `jarvis_comment` к конкретному вхождению — через `notes.occurrence_date` (nullable).
- Существующие события остаются валидными (`rrule is null` = одиночное событие), миграция чисто аддитивная.

## Правила проекта

- **Один этап за раз.** Ничего из следующих этапов не делаем, даже если «это просто».
- **Маленькие шаги.** После каждого шага — инструкция, как проверить руками.
- **Коммит после каждого рабочего шага**, сообщение понятное, на английском, в повелительном наклонении («Add month view grid»).
- **Перед каждым коммитом — тесты:** `npm run lint && npm test && npm run test:e2e` (e2e заодно проверяет `next build`). Красные тесты не коммитим. Новое поведение — вместе с e2e-тестом на него.
- Имитация Supabase (`tests/mock-supabase/server.mjs`) повторяет CHECK-ограничения миграций. Меняешь схему — обнови имитацию и `database.types.ts` в том же коммите.
- **Не добавлять зависимости без необходимости.** Даты — на `Intl` и своих хелперах, свайпы — на touch-событиях, service worker — руками. Новая зависимость = обоснование в коммите.
- **Безопасность данных:** каждая таблица с RLS, политика `user_id = (select auth.uid())`, по одной политике на команду. «Automatically expose new tables» в Supabase выключен → каждая новая таблица требует в миграции явный `grant select, insert, update, delete … to authenticated` (anon — ничего, `grant all` — никогда). Секретный ключ (`sb_secret_…` / `service_role`) никогда не попадает на клиент и в `NEXT_PUBLIC_*`.
- **Проверка входа — в трёх местах:** `src/proxy.ts` (оптимистичный редирект), `requireUser()` в каждой функции `lib/data` и каждом Server Action, RLS в БД. Для авторизации на сервере — только `getClaims()`, не `getSession()`.
- **Схема БД меняется только миграцией** в `supabase/migrations/NNNN_name.sql`.
- Если нужно что-то от владельца (ключи, проект Supabase, настройки) — остановиться и дать точную пошаговую инструкцию.

## Дизайн

- Mobile-first, тёмная тема по умолчанию, минимализм в духе iOS-календаря.
- Интуитивность важнее красоты: с первого взгляда понятно, куда нажать.
- Крупные зоны нажатия (≥ 44px), формы короткие: обязательное поле одно — название.
- Неделя начинается с понедельника.

## Команды

- `npm run dev` — локальный сервер
- `npm run build` — сборка
- `npm run lint` — линтер
- `npm test` — юнит-тесты (секунды)
- `npm run test:e2e` — браузерные тесты (~1 мин): сами поднимают имитацию Supabase (порт 54329) и production-сборку в `.next-test` на порту 3100; реальный Supabase и `.env.local` не трогают. Отчёт о падении — в `test-results/` (`npx playwright show-trace …/trace.zip`).
- Первый раз на новой машине: `npx playwright install chromium`.
- Тесты, завязанные на данные, открывают `?m=2026-10` (данные — в `tests/mock-supabase/fixtures.mjs`); «сегодня» тесты считают сами — от текущей даты не зависят. Браузер в тестах — Chromium с размерами iPhone 13 (Safari/WebKit не проверяется).
